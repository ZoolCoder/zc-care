= Commands
:description: Every zc-care command, flag and exit code.

[cols="1,3"]
|===
| Command | What it does

| `plan` | Read live state and list what would change. The default.
| `apply [FILE]` | Make the changes, then plan again to verify. With a saved plan, exactly those. Targets that were `MANUAL` only because the apply had not installed their tool yet (dotfiles before chezmoi) run in one second pass, unless they delete or need a confirmation, and never from a saved plan; otherwise the apply exits `1` and says how many changes became possible, so you run `apply` again.
| `status` | What is in place per target, without diffing.
| `list` | Every package, app, dotfile and runtime the config declares, one line each: its state, installed version, the app it configures, and why it is there. Then what is installed but declared nowhere.
| `add ITEM` | Declare a package or runtime in one target's manifest, with why it is there. Installs nothing; `plan` and `apply` do.
| `capture` | Print the manifest one target would declare to match this machine. Needs `-target`.
| `validate` | Check the config offline, and each agents manifest, including its `+${keychain:...}+` references.
| `export` | Save what this Mac has, per target, as a JSON snapshot. `-o FILE` writes a file (mode 0600) instead of standard output.
| `diff A.json [B.json]` | What differs between two snapshots, or between one and this Mac. See <<Compare two Macs>>.
| `doctor` | Machine health: binary, system, config, the programs targets need, and each target. It also warns about weak security settings, keys without a passphrase, unsigned commits, secrets in the shell history and risky AI agent configs, each with its fix. xref:security.adoc#_what_doctor_checks[Every check].
| `upgrade` | Save what is outdated to the state folder, then `apply -upgrade`. The review skill reads the snapshot to say what moved from what to what.
| `doctor -fix` | Run `doctor`, then plan a fix for each failing security check that has one, as `sudo` commands where they need root. It lists the exact commands, asks for a yes, runs them and checks again. A finding with no command, such as FileVault, stays advice. After the fixes it reads the fixed checks again and prints `fixed and verified`, `still failing after the fix: NAME` (exit 1), or `could not verify NAME` when a check can no longer be read.
| `undo` | Put back what the last `apply` replaced, or the last `-n N`, or one entry (`-id`, from `-list`). It plans the reverse, shows it and asks first when it uninstalls or overwrites. `-plan` shows it and changes nothing; `-json` prints it. See xref:#_undo[Undo].
| `history` | What was applied, newest first: when, which target, from the terminal, ZC Care or an agent, and whether it worked. Drift changes show here too.
| `drift` | Plan, and save how many changes are outstanding to `~/.local/state/zc-care/drift.json`, which ZC Care shows, with a `manual` count for `MANUAL` items. It exits 1 when it cannot plan. `-last` prints the saved one; `-plist` prints a launchd agent that runs it every morning.
| `init` | Write a starter config for this Mac and save its profiles. Installs nothing. See xref:getting-started.adoc[Getting started] and <<_init_profile_and_skip,Init, profile and skip>>.
| `profile [NAME...]` | Show or set who this Mac is for. A target with `profiles` applies only on a Mac with one of them. See xref:configuration.adoc[Writing a config].
| `skip [KIND:NAME...]` | List or change the packages this Mac does not install. See xref:new-machine.adoc[A new Mac in one command].
| `mcp` | The MCP server on standard input and output.
| `version` | The version.
|===

== Flags

[cols="1,3"]
|===
| `-config FILE` | Config file, or `-` for standard input. Every command that reads the config takes it, `diff` and `export` too.
| `-target NAME` | Limit to this target; repeat for several.
| `-out FILE` | `plan`: save the plan for `apply FILE`. `capture`: write the manifest to `FILE` instead of standard output.
| `-force` | `capture -out`, `export -o`: overwrite `FILE` if it exists.
| `-state LIST` | `list`: only these states, comma-separated, such as `outdated,not declared`.
| `-kind LIST` | `list`: only these kinds, comma-separated, such as `cask,mas`.
| `-adoc` | `list`: the declared packages and runtimes as an AsciiDoc page, one table per section.
| `-why TEXT` | `add`: one line on why the item is there.
| `-section NAME` | `add`: the manifest section to add it under; a new name starts a new section.
| `-item ITEM` | `add`, `remove`: the item as `kind:name`, instead of the first argument.
| `-json` | `plan`, `status`, `list`, `apply`, `validate`, `doctor`, `diff`, `undo`, `history`, `drift`, `init`, `profile` and `skip`: machine-readable. `undo -json` prints the reverse plan and changes nothing; `capture` has no JSON form.
| `-exit-code` | `plan`: exit 2 for changes, 3 for manual-only. `diff`: exit 2 when the two snapshots differ.
| `-upgrade` | `plan`, `apply`: also upgrade outdated packages and runtimes, as if every `packages` and `tools` target said `upgrade: true`.
| `-only RESOURCE` | `plan`, `apply`: only the change to this resource, such as `brew:tmux`; repeat for several. A saved plan remembers `-upgrade` and `-only`.
| `-fix` | `doctor`: plan and apply the fixes, after a yes. Cannot be combined with `-json`.
| `-n N` | `history`: how many entries to show, 20 by default. `undo`: how many applies to revert.
| `-id ID`, `-list`, `-plan` | `undo`: which entry to revert, list them, or show the reverse and change nothing.
| `-yes` | `apply`, `remove`, `undo`, `upgrade`, `doctor -fix`: skip the confirmation prompt.
| `-remove ITEM` | `plan`, `apply`: only uninstall this item, as `kind:name`. `remove` uses it.
| `-via WHO` | `apply`: who asked, for the history; `the terminal` by default. Agents and ZC Care set it; you do not need to.
| `-data DIR` | `undo`, `history`: the folder of the activity log, instead of the default data folder (`undo` also keeps its `undo/` journal there).
| `-last`, `-plist`, `-hour N` | `drift`: print the saved count, print the launchd agent, and the hour it runs at (9 by default, 0 to 23).
| `-o FILE` | `export`: write the snapshot to `FILE`, mode 0600, instead of standard output. Refuses an existing file without `-force`.
|===

`-h` after any subcommand prints that subcommand's flags.

== Init, profile and skip

These three set up a Mac that has no config yet, or a config shared by several
Macs. The walk-through is in xref:getting-started.adoc[Getting started]; the
keys they feed are in xref:configuration.adoc[Writing a config].

`init` writes a starter config and installs nothing; `plan` and `apply` come
next. It puts the packages of other profiles' sections on this Mac's skip
list and saves the Mac's profiles.

[source,console]
----
$ zc-care init -list
$ zc-care init -profile developer -role work
$ zc-care init -profile developer,creative -from-mac -dir ~/dotfiles/zc-care
----

* `-profile p[,p]`: who the Mac is for, comma-separated.
* `-role ROLE`: what it is for, such as `work` or `personal`.
* `-from-mac`: also keep the apps this Mac has installed.
* `-dir DIR`: where to write the config; `~/.config/zc-care` by default.
* `-force`: replace files that are there.
* `-list`: show the profiles and roles, and write nothing.
* `-json`: machine-readable output.

`profile` shows this Mac's profiles; with names it replaces them, and `-clear`
drops them all, so every target applies again. A name is kebab case, such as
`developer`. `-json` prints the list.

`skip` lists the packages this Mac does not install. Pass items as `kind:name`
to add them, and `-undo` to take them off. A skipped package that is missing
stays out of `plan`, `apply` and `drift`; one already installed is untouched.

[source,console]
----
$ zc-care skip cask:ghostty brew:colima
$ zc-care skip -undo cask:ghostty
----

== Compare two Macs

[source,console]
----
$ zc-care export -o mini.json     # on the first Mac
$ zc-care export -o air.json      # on the second
$ zc-care diff mini.json air.json
A mini.json: mini, macOS 15.1, 2026-10-20T08:00:00Z
B air.json: air, macOS 15.2, 2026-10-21T08:00:00Z

packages
  only in B
    cask:ghostty  1.0
  different
    brew:git  2.45.0 -> 2.46.0
----

`export` reads what `list` reads: each target's items with their state and
version, a setting's live value, and the machine's host name, macOS version
and date. A snapshot holds no secrets and no file contents. For a dotfile or a
`localdir` file it holds the path and the sha256 of the live file, so two Macs
compare by hash. An item that is missing, skipped or manual counts as absent.
Installed items that no target declares are in the snapshot too, marked
`not declared`.

`diff` groups by target: items only in A, only in B, and items on both with a
different version, value or hash. With one file, B is this Mac, read live with
`-config`. Targets that match are left out.

== Inventory

[source,console]
----
$ zc-care list
TARGET    KIND     NAME                STATE     VERSION   APP       ABOUT
brew      brew     starship            in place      1.26.0       -         Cross-shell prompt for astronauts
brew      brew     tmux                outdated      3.7c -> 3.8  -         Terminal multiplexer
brew      cask     ghostty             in place      1.3.1        Ghostty   Terminal emulator that uses platform UI and GPU
brew      cask     google-chrome       missing       -            -         -
brew      brew     jq                  not declared  1.8.1        -         Lightweight and flexible command-line JSON processor
dotfiles  dotfile  .config/ghostty/config  in place  -            ghostty   -
runtimes  runtime  node                in place      24.21.0      -         requested lts
----

States:

* `in place`: installed, and nothing newer is known.
* `outdated`: installed, and the manager has a newer version. A pinned
  formula never shows as outdated.
* `missing`: declared, not installed.
* `differs`: a dotfile that does not match its source, or a script still to
  run.
* `manual`: an entry `zc-care` does not install.
* `not declared`: installed on purpose, but no target declares it. For brew
  these are formulae installed on request, casks, taps and App Store apps; a
  dependency never shows.

ABOUT is the item's why, from its manifest line, else the package manager's
description; JSON has both, as `why` and `desc`, with the `section`. Versions
and descriptions come from the package manager; see
xref:providers.adoc[Providers]. A target that cannot be read is listed with its error. The reads run side by side,
so a full list takes about two seconds on a Mac with a few hundred packages.

[source,console]
----
$ zc-care list -state outdated
$ zc-care list -state "not declared" -kind cask,mas
----

== Why each item is there

A manifest says what is installed; its comments say why. A comment at the end
of an entry's line is that entry's why. A comment line that opens a block,
after a blank line or at the top of the file, is the heading of the section
below it. A Brewfile heading can end in profile tags, such as
`# Containers [developer]`, which ZC Care's xref:app.adoc#_choose_apps[app
picker] reads.

[source,ruby]
----
# Git
brew "git-delta" # Side-by-side, syntax-highlighted git diffs
brew "lazygit"   # Git in a terminal UI, opened from tmux with prefix g
----

The same works in apt and dnf package lists and in a mise config's
`[tools]` table: `go = "1.26" # Builds zc-care`.

`list`, ZC Care and the MCP `list` tool show the why. `list -adoc`
turns it into a page that names every tool, links its homepage, and says why
you have it; keep that page in your config repository and generate it again
after a change:

[source,console]
----
$ zc-care list -adoc > docs/software.adoc
----

== Add

`add` writes one entry, with its why, into a target's manifest. It installs
nothing: plan and apply do, so you review the change like any other edit.

[source,console]
----
$ zc-care add -target packages -section Git -why "Fixup commits that find their target" brew:git-absorb
added brew:git-absorb to /Users/me/config/Brewfile; review and install it with: zc-care plan -target packages
$ zc-care add -target runtimes -why "Builds zc-care" runtime:go@1.26
----

* The item is `kind:name`: `brew`, `cask` or `tap` for a Brewfile, the
  manager's name for apt and dnf, `runtime` for mise. A bare name is a
  formula, a package or a runtime.
* A formula or cask from a third-party tap, such as
  `brew:cirruslabs/cli/tart`, brings its `tap` line too.
* A runtime is `name@version`; without a version it asks for `latest`.
* In a manifest with sections, `-section` is required, and the error lists
  them. An item the manifest already declares is refused.
* App Store apps need their id: write the `mas` line yourself.

== Remove

`remove` plans the uninstall of one item, shows it as a DELETE and asks before
it uninstalls the item and drops its line from the manifest, so the next plan
does not bring it back. Apply only ever adds; `remove` is how something leaves.
It is `zc-care apply -remove kind:name`, so `zc-care plan -remove kind:name
-out file` saves the same plan for review, and the apply is recorded in the
history. Pass `-yes` to skip the prompt.

[source,console]
----
$ zc-care remove -target packages brew:htop
DELETE  packages  brew:htop  uninstall with brew and drop it from /Users/me/config/Brewfile
this plan deletes things, overwrites edits made outside the tool or values undo cannot restore, or runs scripts. type yes to continue: yes
$ zc-care remove -target packages mas:409201541
----

An agent cannot remove anything: the MCP `remove` tool only returns a plan, and
a plan that deletes is applied at a terminal.

* The item is `kind:name` as `list` shows it. An item the manifest does not
  declare is still uninstalled, so leftovers go through the tool too.
* An App Store app that is not declared is named by its id.

== Undo

Each `apply` records what it replaced, in `undo/` beside the activity log:
the old value of a macOS setting, the old content of a dotfile, the packages
it installed or removed. `zc-care undo` builds the reverse as a plan, shows
it and runs it through the same engine.

* A setting goes back to its old value and type, or is deleted if it was not
  set before.
* A dotfile, a local-directory file, an agent client's config or rules file
  is restored from a private copy (mode `0600`, never in the history), or
  removed if the apply created it.
* A package the apply installed is uninstalled; one it removed is reinstalled.
  Undo does not edit the manifest: after an uninstall the next `plan` installs
  the package again, and a reinstalled one needs its line added back.

Some changes are listed as `MANUAL` with the reason, because there is no safe
way back: upgrades and runtime installs (no downgrades), dotfile scripts, and
settings that hold an array or a dictionary, which is why `apply` asks before
overwriting one (the plan line says so). Uninstalling and overwriting a file ask first; pass `-yes` to skip the prompt. An undo is itself recorded in
`history` as from `undo`, but it cannot be undone, and neither can
`doctor -fix`. The MCP server does not offer `undo`.

An undo that fails half way remembers what it already put back: the next
`undo` of the same entry skips those and retries the rest. Changes that
cannot be undone exit 3, in two cases. An entry with changes that need a
person stays open and prints `N change(s) must be put back by hand; the entry
stays open`. An entry with only changes that cannot be undone lists them once
and closes, so the next `undo` moves on. An apply that failed while writing a
dotfile keeps a partial record, labelled `partial`, so the file's previous
content can still be restored. Undo refuses to uninstall a cask that adopted
an app already in `/Applications` or `~/Applications`, since removing it
would take the app too.

== State and data folders

The state folder, which holds saved plans, `mcp-audit.jsonl`, `drift.json`
and `upgrades/`, is `$XDG_STATE_HOME/zc-care`, else `~/.local/state/zc-care`.
The activity log and the `undo/` journal live in `$XDG_DATA_HOME/zc-care`,
else `~/.local/share/zc-care`. `history -data` and `undo -data` override the
activity-log location.

== Capture

`capture` writes the manifest that would declare what the machine has: a
Brewfile for brew, one package per line for apt and dnf, and a `[tools]`
table for mise. Use it to start a config from a machine you already set up,
or to see what a manifest misses.

[source,console]
----
$ zc-care capture -target brew > Brewfile.new
$ zc-care capture -target brew -out Brewfile.new
captured brew to Brewfile.new
----

It writes standard output unless you pass `-out`, and it refuses to replace a
file without `-force`. Diff the result against your manifest and copy what
you want; a capture lists everything installed on request, including what
you only tried once.

== Installs ask in the terminal

Apply runs installers attached to your terminal, so `sudo`, a license prompt
or an App Store sign-in can ask you. Their output goes to standard error, so
`-json` output stays parseable.

With no terminal, as under an AI agent or launchd, `sudo` asks for your
password in a macOS dialog instead, through `SUDO_ASKPASS`; Touch ID still
comes first when `sudo` is set up for it. A `SUDO_ASKPASS` you set yourself
is left alone.

== Deletions ask first

A plan with a `DELETE` stops and asks you to type `yes`. Without a terminal,
and without `-yes`, apply is cancelled. Agents never get `-yes`.

== Drift watch

`drift -plist` prints a launchd agent that runs `drift` at 9:00 (`-hour`
moves it). Keep it in your dotfiles and loaded by a `services` target, like
any other agent:

[source,console]
----
$ zc-care drift -plist > Library/LaunchAgents/dev.zoolcoder.zc-care.drift.plist
----

The agent carries the `PATH` of the shell that printed it, since launchd
starts agents with almost none. It only plans; nothing is applied. A change
in the count is written to `history`; ZC Care counts the changes in its
number, on the menu bar and in SketchyBar's `zccare` item.

== Exit codes

[cols="1,3"]
|===
| `0` | Nothing to do, or the apply converged and was verified.
| `1` | Something failed.
| `2` | With `-exit-code`: changes are outstanding, or `diff` found a difference.
| `3` | With `-exit-code`: nothing left but `MANUAL` items. `undo`: the entry had changes that cannot be undone, listed for you. Changes that need a person leave the entry open; an entry with only un-undoable changes closes.
|===
